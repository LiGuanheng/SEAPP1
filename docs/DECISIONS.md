# 设计决策记录（Decision Log）

> 格式：`D-xx｜决策｜状态｜决策者`。
> **状态说明**：`用户明确选择` = 用户在设计文档中已写明；`AI 提议·待学生验收` = AI 为实现做出的技术取舍，需学生复核；`AI 决定·已记录` = 影响较小、AI 自行决定并留痕。

---

## D-01 技术栈：Phaser 3 + TypeScript + Vite

- **状态**：用户明确选择（任务书第 1.4 条）
- **理由**：Phaser 提供成熟的精灵、动画、Tilemap、相机、输入与场景管理；Vite 提供极快的开发服务器与静态构建；TypeScript 保证核心逻辑可测试、可追溯。
- **版本（实测锁定）**：phaser 3.90.0 / vite 7.3.7 / typescript 5.9.3 / vitest 3.2.7。
- **代价**：Phaser 包体约 1.2MB（gzip 后 ~350KB），首屏稍慢；通过代码分割与静态托管缓存缓解。

## D-02 UI 使用原生 DOM，而不是 Phaser 文本或 React

- **状态**：AI 提议·待学生验收
- **理由**：
  1. 中文排版、长文本、滚动列表、按钮禁用态在 DOM/CSS 下质量与开发效率远高于 Phaser Text；
  2. 课程项目不需要前端框架，引入 React 会增加构建复杂度与包体，收益低；
  3. 战场仍是 Phaser，DOM 只做覆盖层，二者职责清晰。
- **代价**：需要自己管理屏幕生命周期（`Shell` 负责卸载与键盘监听清理）。

## D-03 战役逻辑与渲染分离，核心可 headless 运行

- **状态**：AI 决定·已记录（依据任务书 NFR-04 与测试要求）
- **理由**：把经济、日结算、存档、战斗模拟写成纯 TS，可在 Vitest 中直接跑完整战役与战斗，不需要浏览器。这让「证明游戏可通关」成为自动化测试而不是口头声明。
- **代价**：渲染层需要每帧从 sim 读状态同步精灵，多一层数据拷贝（已用对象复用控制）。

## D-04 寻路采用「流场（Dijkstra）+ 障碍高代价」而非逐单位 A*

- **状态**：AI 提议·待学生验收
- **理由**：
  1. 300+ 单位逐帧 A* 必然卡顿；流场每格只存一个方向，单位查询 O(1)；
  2. 墙体作为**高代价可通行**格，天然产生「尸潮涌向最薄弱的墙/门并开始拆墙」的行为，无需额外编写破墙决策；
  3. 墙段摧毁后只需把代价改回可通行并重算一次流场。
- **代价**：单位不会做复杂的绕后微操；对 V1 的「尸潮攻城」体验而言可接受。

## D-05 地图固定 160×112 格 / 32px 瓦片

- **状态**：AI 提议·待学生验收（GDD 给出的基准，未改动）
- **理由**：满足「一张连贯大地图」与「两条以上路线」的空间需求；5120×3584 世界像素在 0.35–1.2 倍缩放下均可读。
- **代价**：单张地图内容密度需靠道路、废墟、据点填充；V1 只做一张图。

## D-06 墙段使用固定分段对象，不做逐像素破坏

- **状态**：AI 提议·待学生验收（GDD 明确建议）
- **理由**：可预测的碰撞更新、可靠的跨日持久化、清晰的损伤美术三档；每段记录 `hp / destroyed`。
- **代价**：破坏位置不完全自由；玩家不能在任何位置凿洞。

## D-07 人类 AI 采用「预算 + 固定槽位 + 优先级列表」

- **状态**：AI 提议·待学生验收
- **理由**：可解释、可测试、可被玩家针对（拆兵工厂 → 不能建塔；拆军营 → 补兵下降）。避免"每回合白送一支军队"的假 AI。
- **代价**：行为不够狡猾，不会做复杂欺骗；V1 可接受。

## D-08 战斗节奏：普通攻城 4 分钟、终局 6 分钟

- **状态**：AI 提议·待学生验收
- **理由**：匹配 GDD；4 分钟内足以完成一次「破一段墙 → 推进 → 拆一个设施」的战术循环，失败也不至于浪费太多时间。
- **代价**：大地图远端据点单场打不完，需要多日推进——这是设计意图。

## D-09 数值全部集中在 `src/config/balance.ts`

- **状态**：用户明确要求（任务书第 4 条）+ AI 实现
- **理由**：便于按试玩结果调参，并在 `docs/BALANCE_NOTES.md` 记录每次改动与原因。
- **代价**：配置对象较大，需要类型约束避免拼写错误。

## D-10 存档只保存战役状态，不保存战场精灵

- **状态**：AI 决定·已记录
- **理由**：战斗中刷新恢复到战前议事厅，比尝试序列化 300 个精灵更可靠；战役状态（天数、资源、墙段、据点、设施）完整保留，符合"不丢失一局战役"的要求。
- **代价**：当前这一场战斗的进度会丢失；UI 会明确提示。

## D-11 美术：战场素材程序化原创绘制 + AI 生成关键视觉

- **状态**：AI 决定·待学生验收
- **理由**：
  1. 战场需要**大量一致的多帧动画**（10+ 单位 × 6 状态），AI 生图难以保证帧间一致与透明边缘；程序化绘制可精确控制调色板、比例、动画，且完全原创、无授权风险。
  2. 菜单主视觉、结局插画属于单张高冲击力画面，适合用图像模型生成，成本低、效果好。
- **代价**：程序化像素画风偏"16-bit"，与 AI 插画存在风格差异；通过统一的暗紫/幽绿/骨金配色与噪点叠加缓解。

## D-12 不引入后端、数据库与账号系统

- **状态**：用户明确选择（任务书"不引入数据库、后端登录、付费 API"）
- **理由**：纯静态即可满足课程验收与公开访问；存档用 localStorage。
- **代价**：无法跨设备同步存档；已在用户手册中说明。

## D-13 测试框架选 Vitest（而非 Jest）

- **状态**：AI 决定·已记录
- **理由**：与 Vite 共享配置与 ESM 解析，零额外 transform 配置；`npm run test` 一条命令即可。
- **已知问题**：vitest 3.2.7 的传递依赖 `tinypool` 存在 npm audit 报告的 dev-only 漏洞。**仅影响本地开发/测试进程，不进入构建产物**；升级到 vitest 5 属破坏性变更，V1 不冒险，已在测试报告中记录。

## D-14 难度参数

## D-15 关键操作键位

- **状态**：用户文档给定（GDD §7.2）+ AI 统一
- **最终键位**：`1–5` 兵种卡、`Q/W/E` 君主技能、`WASD` 镜头、`空格` 居中、`P` 暂停、`Esc` 取消、`F` 终局全军冲锋。
- **冲突处理**：`W` 同时是「镜头向上」与「技能 2」。**决定：镜头用 WASD，君主技能改用 `Q` `E` `R`**，避免同一按键两种语义。UI 键位提示以实际实现为准（任务书要求"文档一套、游戏另一套"不可接受）。
- **注**：这一改动偏离 GDD 原文，属于 AI 提议，需学生验收。

## D-16 单位与建筑命名

- **状态**：AI 提议·待学生验收
- **理由**：用户给定「普通丧尸/疾行者/重装感染者/蜘蛛」，为统一暗黑奇幻语感，UI 采用「食尸鬼 / 疾行者 / 重装感染者 / 蛛行者」，代码内部分别为 `zombie / runner / brute / spider`。

## D-17 活动单位上限

- **状态**：AI 决定·已记录
- **值**：普通战 260、终局 320（可通过画质档下调至 180）。
- **理由**：保证 1366×768 笔记本核显也能维持可操作帧率；超出库存排队入场，不丢失兵力。
- **待验收**：需在目标机器上实测后回填 `docs/TEST_REPORT.md`。
